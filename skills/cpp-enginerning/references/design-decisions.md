# 结构调整的判断规则

只针对当前任务做取舍。下面是工程裁决，不是通用尺寸指标。

| 观察到的信号 | 采取的动作 | 反例与停止条件 |
| --- | --- | --- |
| 一段逻辑有领域名称、独立契约或不同抽象层次 | 提取函数，并检查传参、作用域、销毁时点和调用顺序 | 提取导致共享可变状态到处传递，或只是 `step1/step2` 包装时保留局部结构 |
| 调用者被迫了解内部步骤和状态 | 收拢为完成一个概念的接口，明确失败、寿命和线程条件 | 不隐藏资源限制，不为了接口少而加入万能 Context |
| 同一规则在多个入口重复变化 | 提取最小纯规则，入口保留各自副作用 | 仅文本相似、政策/变化原因不同不合并 |
| 共用函数为不同调用者累积开关与分支 | 先内联到各调用者，消除不适用分支，再判断真正共享部分 | 不把所有参数化算法判为错误抽象 |
| 模块因多类无关需求反复修改 | 在内部先划分职责，再迁移边界和依赖 | 文件长本身不是拆模块的充分证据 |
| 当前需求需要测试或替换一个外部系统 | 使用最小接缝及现有适配方式 | 不为假设的多个后端新建框架；有真实第二实现、测试替身或部署边界时重新评估 |
| 审查意见仅表达个人风格 | 标为非阻塞，并优先服从仓库风格 | 正确性、兼容性及明确团队约定不是个人偏好 |

## C++ 语义核对

提取前写出资源/锁的“获得 → 最后使用 → 释放”顺序。提取后仍需覆盖早退和异常路径；返回值相同不说明作用域等价。
把语句合并为函数参数前确认求值顺序，不依赖未指定顺序。保存引用或视图必须有独立寿命依据。

“没有行为改变”以约定的可观察契约为准；测量开销、异常类型、回调线程、资源回收或 ABI 如属契约，就要单独验证。
不能把 UB 的一次观察结果固定为合法契约。修复 UB 与结构整理分步说明。

## 规则冲突时

先核实语言/平台事实，再满足当前需求和项目契约；通用建议只在适用时使用。项目风格不会让悬空引用或数据竞争变得合法。
遵循项目错误机制、语言版本、分配器和 ABI 政策；不把 Core Guidelines 的默认建议转成跨项目硬规则。
当多个方案都满足契约，选择更少概念、较小改动和较低验证成本的一项。功能完成并达到质量门槛即可，不以完美为验收条件。

依据：Fowler 的行为保持定义与 YAGNI、Sandi Metz 的错误抽象分析、Google 代码审查标准。链接见 [sources.md](sources.md)。
