# 接口、值语义与失败保证

用于新能力、公共 API、核心状态类型或非平凡接口修改；只填写影响当前决策的内容。

## 先写调用契约，再选择类型

从真实调用者出发，给接口说明以下六点，可写在任务卡/声明旁，不强制创建文档：

1. 输入域与单位；空值、空集合、极值和非法组合是否允许。
2. 谁拥有/借用状态与缓冲区；返回值/视图何时失效，是否允许异步保存。
3. 成功后哪个不变量成立；失败时输出参数和已提交副作用是什么状态。
4. 是否阻塞、在哪个线程调用/完成；能否重入、并发调用或取消。
5. 兼容性边界：源码、二进制、线协议/配置、持久化分别承诺什么。
6. 已有成本预算：分配、拷贝、等待、队列容量；未知项不凭空填写。

先做一条完整业务路径和边界测试，再决定需不需要扩展点。能用现有值类型、函数或局部适配表达时，不自动增加继承层次、全局 service locator 或事件总线。
重复易混淆的单位/标识符可用项目已有强类型表达；不要为所有整型一律生成 wrapper。

## 值语义与资源类型

- 优先让现有 RAII 成员管理资源；有自定义析构/复制/移动时逐一核查五种特殊成员的生成、删除和语义，不机械手写整套代码。
- 明确复制是独立值还是共享状态；只有真实共享所有权才选择 shared_ptr。引用计数不等于对象线程安全。
- 明确移动后允许的操作。标准库多数类型移动后是有效但状态未指定，不能一概断言“为空”；用户类型以自身契约为准。
- 自管理句柄要测试无效句柄、移动构造/赋值、已有资源被替换、错误路径释放和重复释放；自移动行为按其约定验证。
- 有多态销毁时验证实际删除路径；不要为了测试就把所有函数虚化。新增虚函数/析构策略要同时看 ABI。

## 失败保证与提交点

区分：不泄漏且不变量仍成立（基本保证）、失败时可观察状态不变（强保证）、约定操作不失败。选择必须来自接口需要与实际可实现性，不默认宣称每个 API 都有强保证。

需要强保证时先完成可能失败的准备，再在可兑现的提交点更新状态。外部 I/O、远端请求、设备动作不能仅靠本地 RAII 回滚；明确补偿、幂等或部分成功语义。
不要把添加 `noexcept` 当作实现不失败：异常逃出不抛出边界会终止；检查调用链、分配、转换及回调。异常关闭环境沿用已有错误返回/创建工厂规则。
失败注入应针对真实可失败接缝，检查资源和旧状态；不要引入全局不稳定的分配钩子来验证普通私有重命名。

## 公共依赖与泛型接口

公共头核对自包含 include、ODR、宏/条件编译、可见性与安装后的消费者依赖。CMake 的 PUBLIC/PRIVATE/INTERFACE 依据真实使用需求选择，不能为链接过关一律扩大传播范围。
模板/重载修改编译代表性消费者：预期接受的类型、应拒绝的类型、const/lvalue/rvalue、隐式转换与歧义。Concepts 能约束语法，不自动证明语义或复杂度；项目低版本不为此升级标准。
不要仅为减少上下文改为 header-only、PImpl、类型擦除或 C++ modules；这些选择有构建、ABI和运行成本，先列具体受益者。

## ABI 的具体边界

区分“消费方重编译后通过”和“旧二进制仍可工作”。布局、对齐、vtable、导出符号、调用约定和标准库 ABI 都可能影响后者。
确定项目支持的工具链/标准库/编译选项矩阵；同一函数名或一次链接成功不证明兼容。需要旧二进制承诺时保留旧消费者，验证契约和对应 ABI 检查；目标环境缺失则报告缺口。
标准库 Dual ABI、平台 ABI 规范是具体实现边界，不意味着所有 C++ 平台共享一套 ABI。
