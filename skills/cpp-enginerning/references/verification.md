# 按风险选择验证

## 先确认检查真的执行

记录平台、编译器/标准库、构建配置、命令、退出码、诊断、实际用例/目标数及覆盖边界。
对过滤后的测试先确认名称和非零数量；CTest 支持时使用 `--no-tests=error`，旧版本则显式检查发现/执行结果。全部 skip 也不能记为行为 PASS。
测试内部的 `assert` 若被 `NDEBUG` 禁用，成功退出不能验证那些断言；使用可靠测试框架或明确保留断言的配置。
不要将配置成功、编译成功、runner 成功和测试通过混为一项；已有失败记录基线，新的失败单独归因。

| 改动 | 最小相关证据 | 按风险扩大 |
| --- | --- | --- |
| 私有纯逻辑/命名 | 受影响目标编译、相关契约用例 | 边界、失败和原缺陷回归 |
| RAII、借用、容器失效 | 正常/早退/异常路径，资源释放次序 | 目标工具链支持的 ASan；相应 UB 检查 |
| 共享状态、锁、异步销毁 | 确定性控制交错/重入/取消/迟到完成测试 | 支持环境的 TSan、压力运行；人工核对同步关系 |
| 公共头/API/ABI | 消费者构建、接口和协议用例 | 支持矩阵；必要时旧二进制消费方与布局/符号检查 |
| parser、长度/整数转换 | 空、极值、非法输入、错误时输出状态 | 有现成设施时性质测试或 fuzz；不强制引入新框架 |
| 热路径 | 相同配置/输入的前后基准及正确性检查 | 原始样本、分配数、尾延迟、端到端和目标硬件 |

## 构建与静态分析

- 使用仓库 preset/target/toolchain。CMake 的标准属性可能允许回退，核对实际编译命令、`CXX_STANDARD_REQUIRED`/compile features 和库可用性；不在本次任务中擅自改变政策。
- clang-tidy 使用匹配配置的 compilation database 和现有 `.clang-tidy`。头文件通过真实消费者检查；不要把宏、include 或目标架构不匹配的输出直接当作代码缺陷。
- 先诊断后修复，不默认开启全量 `-fix`、全部 modernize checks 或给遗留工程全局添加 `-Werror`。受影响范围之外的历史告警单列。

## 动态检查的证据边界

- ASan 检查执行到的地址/寿命问题；UBSan 检查其启用项覆盖的未定义或可疑操作。它们不能替代完整契约测试。
- UBSan 的许多检查可以报告后继续执行。采用项目支持的 fail-fast 配置，或将 sanitizer 诊断纳入失败判定；退出码 0 不足以判 PASS。
- TSan 检查执行到的竞争；未插桩依赖、平台支持与工作负载限制都影响证据。通过一次运行不证明所有调度正确，也不证明无死锁。
- 使用分别支持的构建配置，核实 sanitizer 组合；不把 ASan 和 TSan 强塞进同一构建。运行时未能启动记 BLOCKED，不记为源码缺陷或通过。
- 仅为复现当前风险配置检查；没有目标硬件时用本机证据限定结论，不填写目标平台数据。

## 性能验证

先写清指标（单次耗时、吞吐、排队/端到端延迟、分配或内存），再量基线。记录编译优化、LTO、CPU/架构、输入、线程数、计时范围、预热和重复运行方法。
确认被测工作未被编译器消除；即使使用 `DoNotOptimize` 也检查输入和优化行为。对冷启动问题保留冷路径，不用预热抹去问题。
保留原始结果并报告波动；小于噪声的差异记为无结论。微基准平均值不能充当系统尾延迟，instrumented/debug 结果不能冒充发布性能。

## 交付状态

- PASS：这项检查确实执行，并满足其标准；同时写明范围。
- FAIL：该检查发现不满足标准的证据，区分既有失败与本次回归。
- NOT RUN：没有执行，写出原因和下一步。
- BLOCKED：尝试所需步骤但因工具、依赖、环境或权限无法完成，保留具体错误。

这些状态适用于每项证据。某一项 PASS 不代表整个任务已完成。
工具细节来自官方文档；精确版本与参数以项目安装版本为准，见 [sources.md](sources.md)。
