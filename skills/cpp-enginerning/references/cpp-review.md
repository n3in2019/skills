# C++ 审查：语言合同与执行合同

只检查本次改动相关的部分，先核实实际配置，再按风险选择以下段落。
以下检查表是综合工程规则；不宣称来自任何书的原版检查清单。

## C1. 先确认实际配置

读取 CMake/构建脚本、presets、工具链和 CI：语言标准、编译器与标准库、目标平台、
异常/RTTI、链接方式、可见性、分配器、sanitizer 及公开 ABI 策略。
未知项标记 unknown；不要从另一个项目、文件名或本地编译器默认值推断整个工程。

保持当前标准。不在 C++17 项目直接引入未经确认的 C++20/23 标准库类型。
项目自定义的 Result/TRY/Task 等需要找到定义，不得伪称标准设施或凭空调用。
“头文件存在”不等于目标构建可用；有疑问时使用真实目标配置做最小编译验证。

新接口或核心值类型涉及复制/移动、失败保证及消费者依赖时，补读 [api-design.md](api-design.md)。

## C2. 所有权与借用

对新接口逐项问：谁创建、谁拥有、谁释放、何时失效、能否为空、是否跨线程或异步存留？
优先使用能表达真实责任的现有值类型或 RAII 句柄；遵守项目已选分配机制。
不要因为裸指针出现就自动换成 shared_ptr；它可能是合法借用，也可能是真正的所有权漏洞。

检查：
- 引用、span/string_view 等视图是否超出底层对象寿命；异步代码是否保存了借用。
- 容器扩容、擦除、移动或缓冲区归还后，指针、迭代器和视图是否仍被使用。
- 自定义资源包装是否恰好释放一次；失败路径、移动后对象和部分构造是否安全。
- 捕获 this 或引用的回调是否可能晚于对象销毁；循环共享拥有是否导致资源无法退出。
- 共享拥有是否只延长寿命，却被误认为也保护了对象的可变数据。

不能为减少拷贝而引入悬空借用，也不能用复制大 payload 掩盖本应明确的生命周期合同。

## C3. 提取函数可能改变 C++ 语义

特别检查局部对象的构造/析构时点、锁的作用域、临时对象寿命、返回类型、重载选择、
值类别、别名关系、求值与副作用次序，以及失败时谁负责清理。

将一段代码移出锁区或移入辅助函数时，逐项核对共享状态保护与资源有效期。
对数值代码核对精度、溢出前提、NaN/边界和允许的浮点容差；不能为获得通过临时放宽容差。
不要给每个返回值加 std::move，也不要以“减少复制”的直觉替代目标构建中的验证。

## C4. 错误、异常与 noexcept

使用所在模块的错误合同；不要因书中偏好而全局改成异常或状态码。
若公共边界要求不抛异常，逐路径检查依赖调用、分配、字符串/容器构造及回调。
仅加 noexcept 不是错误处理；需要可兑现的失败策略和验证。
不要吞掉错误，不把失败变成默认构造的成功结果；不要在无异常构建中凭空添加 try/catch。

检查错误传播是否保留诊断上下文、取消与失败能否区分、重试是否会重复外部副作用。

## C5. 并发与执行域

为共享可变状态标记保护机制与访问线程；有必要时明确锁顺序和事件先后关系。
优先避免在持锁期间调用未知回调；若遇到既有此类路径，先核实重入与锁契约，再决定修复范围。把回调移到锁外后，要重新验证所传数据的寿命、快照语义和重入。
不要使用 detach、全局锁或“所有东西改成 atomic”作为通用修复。

检查等待是否有清楚条件和退出路径、关闭时是否仍可能产生回调、队列满时如何处理。
跨线程、协程挂起与完成时，要说明哪一方持有状态；避免把借用或锁无意带过挂起点。
对 coroutine lambda 分别核对闭包和协程帧的寿命；按值捕获 shared_ptr 不自动保证闭包在恢复时仍存在。对引用参数、this 和 view 分别追踪被引用对象，不能用“已经复制到帧”概括其寿命。
使用项目已有 executor/domain，不为了小组件自动新增线程、线程池或调度框架。
静态检查或一次压力测试不能证明所有调度安全；在报告中保留证据边界。

具体状态竞争与确定性测试选择见 [async-contracts.md](async-contracts.md)。

## C6. 异步生命周期与取消

接口需区分接受请求、执行中、停止中和终态；具体状态采用仓库既有定义。
确认超时/取消后在途工作如何结束，回调能否迟到，重复完成如何处理，谁负责释放资源。
必要时采用请求标识、generation 或其他已有机制排除过期结果，不无条件新增一套框架。

取消一个任务不代表物理设备已经停止；软件结果不能替代设备确认或独立安全机制。
析构前必须满足已约定的无在途访问条件；不以“返回了 cancelled”直接推断缓冲区可复用。

## C7. ABI、API 与物理依赖

公共结构布局、虚函数表、导出符号、调用约定、模板/内联实现、默认参数及错误合同变化要单独审查。
核对消费方、插件、序列化和构建配置，区分源兼容与二进制兼容。
PImpl、类型擦除或“保留函数名字”不能自动证明 ABI 安全。

公共头应只暴露契约需要的依赖；检查新增 include 和 target 依赖是否形成环或扩大重编译范围。
ABI 稳定范围以项目明确政策为准，不能擅自承诺独立厂商插件或跨工具链兼容。
删除符号前检查注册、动态加载、脚本、条件编译和外部文档，而不仅是源码引用计数。

## C8. 性能与热路径

将新增成本落实到路径：分配、payload 复制、锁、间接调用、缓存访问、排队、线程切换、IPC。
不要为“统一架构”强迫同进程调用走序列化，也不要先验认为所有包装都能被编译器消除。
接口清楚与执行便宜都要验证，不以函数短或使用 inline 关键字作为性能证据。

使用与基线相同的目标、构建、负载与采样方法；根据需求报告尾延迟、吞吐、内存和分配等指标。
缺少目标硬件时不填写目标平台结果。instrumented/debug 构建的结果不能不加说明地代替发布性能。
