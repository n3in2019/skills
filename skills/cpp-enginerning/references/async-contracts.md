# 异步与并发契约

先读取项目真实 Task/Executor/Operation 定义；本文件不提供新调度框架，也不假定项目采用某个协程库。

## 接受、取消、完成、销毁分别判断

| 阶段 | 必须确认 |
| --- | --- |
| 请求接受 | 拒绝/队列满如何报告；输入是在调用时复制、转移还是借用 |
| 执行中 | 状态持有者、执行线程、允许重入点、共享数据的同步依据 |
| 请求取消/超时 | 哪个状态改变；是否仅抑制业务结果；底层工作和回调是否仍可能在途 |
| 终态交付 | 允许完成几次、成功/失败/取消如何竞争、重复/过期完成如何处理 |
| 销毁/资源复用 | 什么证据表明不再访问对象或缓冲区；是否需要 drain/join/ack 或已有寿命句柄 |

取消请求不是停止确认。即使业务已经超时，也不立即推断设备/线程/回调已放弃访问。
若复用 session/operation，检查旧完成是否能写进新任务；使用现有 request id/generation 或每次操作状态，并确定溢出/复用策略。不无条件添加全局任务框架。

## 回调与协程

分别画清闭包对象、协程帧、this、引用/视图及底层资源的寿命；不要把它们统称为“捕获了”。
捕获式 coroutine lambda 的闭包可能先于恢复被销毁；shared_ptr 的按值捕获也不能自动延长闭包。优先采用已验证的具名 coroutine 与拥有型值参数，或明确保活闭包的现有模型。
协程值参数若只是 view/pointer 仍是借用。核对初始挂起、每次恢复、终止/取消和帧销毁；持有 coroutine handle 不一定拥有全部引用对象。
禁止无依据地复制 handle 所有权或重复 destroy/resume；使用项目已定义的完成与销毁规则。

## 并发与重入

先确定真实线程合同，单线程队列不凭空报告数据竞争；单线程仍可能有重入和迟到完成。
修改锁时列出保护的数据、锁顺序与回调边界。将回调移到锁外要核对状态快照/寿命；不能只删除锁。
修改原子操作/内存序时说明跨线程状态发布的同步关系；`volatile` 不是线程同步，单个原子字段也不自动保护整个对象。不无证据追求 lock-free。
检查执行器线程里同步等待自身任务、取消回调重入、关闭时新请求、排队上界和背压；这些需要具体调度证据，不能凭命名判断。

## 确定性验证优先

用项目现有测试执行器、可控 promise/barrier 或手动完成队列安排交错，避免仅靠 sleep 猜顺序：

- 接受 → 取消 → 旧完成；接受 → 超时 → 新请求 → 旧完成 → 新完成。
- 完成重复投递；回调内提交新请求；所有者销毁后队列清空。
- 错误/队列满时状态与资源归属；停止确认前缓冲区不复用。

按合同选择上述用例，不能把不可能的调用次序当作确定缺陷。再辅以支持平台的 sanitizer/压力检查，并标注其覆盖边界。
