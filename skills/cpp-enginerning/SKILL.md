## 1. 明确模式与最小上下文

- 区分 review（默认只读）、refactor（保持约定行为）、bugfix（修正指定旧行为）、feature（完整需求路径）、perf（先测量）、migration（明确兼容范围）。混合任务分步验收。
- 读适用的分层 `AGENTS.md`、工作区状态和已有 diff；保留用户改动。再沿入口/接口 → 实现 → 直接调用者 → 相关测试 → 构建/CI 定位证据，先 `rg` 搜索再定向阅读。
- 查真实目标的标准、编译器/标准库、宏、工具链和测试命令。生成代码、注册、动态加载、配置或 FFI 消费方不能仅靠符号搜索排除。不要用截断片段判断完整函数。
- 对非平凡修改写短任务卡：目标 / 非目标 / 拟改文件 / 允许变化 / 不变量 / 验证。机械小改无需长计划或新文档。
- 契约覆盖输出、错误、副作用顺序、资源寿命，以及相关时序/成本；区分明确需求、已观察行为和未知事实。发现未定义行为时不能承诺保持其输出，单列缺陷与修复范围。
- 每次扩读回答具体未知点；当已能确定修改边界、受影响消费者和验证观察点就开始工作。事实无法查明且影响正确性时询问，独立部分继续。

## 2. 选择最小完整改进

- 优先修复当前任务的具体痛点。必要重构与行为改变分步，不附带格式化、公开重命名、依赖升级或线程/异常模型迁移。
- 用领域含义命名；必要时表达单位、所有权和副作用，遵循当地风格。注释说明原因、约束和取舍。
- 按独立概念与变化原因划分函数/模块；核对接口是否让调用者无需阅读内部就能正确使用。不要按行数拆分，也不要制造跨文件微小包装。
- 只合并具有同一业务规则和变化原因的重复；抽象若靠越来越多的模式参数维持，允许内联并重新划界。
- 对非显然抽象比较现状与最简单改进：收益、消费者影响、生命周期和执行成本。参数多是调查信号，不是自动添加参数包或上下文对象的理由。

## 3. 建立基线并小步实施

1. 从仓库真实命令建立相关基线，确认实际执行的目标和测试数量。零测试、跳过和运行器成功不等于行为通过。
2. 缺陷用例应旧实现失败、新实现通过；纯重构的契约用例前后都通过。缺少保护时先补关键正常/边界/失败观察，不复制实现为断言，也不重写需求。
3. 每步变换一个清晰概念，检查 diff 和对应验证再继续。提取函数尤其核对析构时点、锁作用域、异常清理、引用/视图及求值顺序。
4. 保持项目错误契约。检查分配失败、部分状态更新、取消和重试的副作用；不要靠吞错误、放宽断言、关闭检查或升级标准来过关。
5. 基线失败时区分既有失败、新回归和环境阻塞。只能撤销自己可识别的改动；不要清理用户工作区。验证缺口限制结论和改动范围，不自动触发全面重写。

## 4. 验证、停止和交付

- 按改动风险选择构建、静态检查、契约测试、sanitizer、消费者/兼容或性能验证，细则见 verification。改头文件时编译相关消费者；改并发不能只测顺序输出。
- 目标达成、必要验证通过、diff 范围可解释时停止。下一步若只是风格偏好或需要无关重设计，记作后续项。关键契约冲突或必需验证受阻时明确报告，不声称全部完成。
- review 列出文件/符号、触发条件、后果、证据和最小建议，按影响排序；区分确定缺陷、待确认风险和非阻塞风格意见，不擅自修复。
- 实施交付：行为保持/改变、关键取舍、实际命令/环境/测试范围、PASS / FAIL / NOT RUN / BLOCKED、剩余风险。检查日志，不仅看退出码；不将本机结果冒充目标平台或有限测试冒充证明。
- 长任务检查点只保留路径/符号、契约、决定、已执行证据和下一步；不要复制整个文件。提交/推送遵循当前任务授权。
