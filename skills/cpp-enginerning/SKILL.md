# C++ Engineering

## 0. 选择任务模式

先区分 review（默认只读）、refactor（保持外部行为）、bugfix（明确修正的旧行为）、feature（最小完整需求）、perf（先测量）、migration（明确兼容与迁移范围）。混合任务分步验收，不能借重构改变 API、线程或异常政策。

C++ 任务读 [cpp-review.md](references/cpp-review.md) 的配置段和本次风险相关段；设计和验证规则留在下方。无需加载整个集合或无关机器人检查。

## 1. 获取足够且有限的上下文

1. 读适用的 `AGENTS.md`（根目录及目标路径）、README 的构建/测试段、工作区状态和现有 diff；保留用户改动。
2. 用 `rg --files` 定位目标，用 `rg` 查符号；先读目标实现、公开接口、直接调用者及相关测试。从 CI/构建配置确认命令，不猜造验证结果。
3. 仅当所有权、错误传播或跨模块契约有未知点时，沿相关调用链继续读。每次扩读回答一个具体问题，不批量加载无关模块或全部规则。
4. 修改前记录短任务卡：目标行为、保持的契约、拟改文件、验证命令。契约包括输出、错误、副作用顺序、资源生命周期，以及相关时序/性能约束。
5. 信息不足先找证据；无法从仓库确认且会影响行为时再询问。长任务保留检查点（文件/符号、决定、测试结果、下一步），避免重复加载。

## 2. 限制范围并选择边界

- 将功能修复与行为保持的整理分成可验证的小步，每步只做一种变换。必要重构限于阻碍当前任务的代码，额外清理记录为后续项。
- 用领域含义命名；单位、所有权或副作用会影响理解时明确表达，沿用当地风格。公开重命名先查调用者和兼容要求，不顺手全仓库改名。
- 当逻辑有独立含义、混合抽象层次或可独立验证时提取函数。若需要传递大量共享可变状态，或只能命名为 `process_part2`，重新判断边界；不按行数拆分。
- 当职责有独立变化原因且能形成小而明确的接口时拆模块。先在原模块内建立边界，再迁移；不因文件长或“以后可能复用”新建框架或接口层。
- 比较重复代码的业务规则、错误和变化原因；同一规则重复才提取最小公共逻辑。形状相似但语义不同保留各自实现，避免标志参数驱动万能函数。
- 注释解释原因、约束和非显然取舍；可由代码表达的动作使用命名表达，保留有用的契约说明。

## 3. 保护行为再修改

1. 先运行相关现有测试建立基线。逻辑改动缺少保护时，先补可观察行为的特征测试：正常、边界、失败及副作用；不把实现逐行复制为断言。
2. 缺陷回归用例应修改前失败、修改后通过；重构用例前后都通过。保留现有怪异行为，除非任务要求修正，并单独说明行为变化。
3. 每步运行最相关验证；失败则定位该步并修复或回退自己的改动，不删测试、放宽断言或吞错误获取通过。
4. 保持原错误契约；按项目约定传播或在明确边界转换错误并保留上下文。禁止失败当成功、无界重试或重复记录同一错误；检查失败/取消路径的资源清理和部分副作用。
5. C++ 检查生命周期、借用/所有权、析构/异常路径、移动/复制与公开 ABI；保持项目语言版本和异常政策。性能敏感路径检查新增分配、拷贝、锁与调度变化，需要时测量，不凭代码宣称性能等价。

## 4. 停止与提交前自检

当目标满足、相关验证通过且 diff 可解释时停止。若下一步需要无关 API 变更、新依赖、跨模块重设计，或缺少可靠验证，就停止扩展重构并记录限制。必需工作受阻则报告阻塞，不宣称完成。

- 审查完整 diff 和工作区状态：每处修改是否服务任务？有无无关格式化、调试残留、生成物或用户改动被覆盖？
- 按影响范围运行既有格式/静态检查、受影响目标构建和相关测试；公共契约或跨模块改动扩大到调用者/集成验证。通过后不无理由重复运行。
- 无法运行时说明原因及剩余风险；静态审查不能称为行为验证，有限测试不能称为所有输入的等价证明。
- 交付说明行为变化或保持的契约、重构理由、验证命令与结果、未验证项；仅在任务授权时提交/推送。

## 审查和验证证据

审查按影响排序，列出文件/符号、触发条件、后果、证据和最小建议；区分缺陷、待确认风险与风格偏好。无发现不代表无缺陷。
验证记录平台、实际命令与覆盖范围，明确 PASS / FAIL / NOT RUN / BLOCKED；不沿用其他项目的结果。性能改动使用可比构建、输入和目标；没有目标硬件就保留缺口。
对非显然的抽象，比较保持现状与最简单改进，说明收益、隐藏成本及消费者影响。允许内联函数或拆除错误抽象；不为了上下文限制制造跨文件微小包装。
